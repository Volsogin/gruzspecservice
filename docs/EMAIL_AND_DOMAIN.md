# Почта, домен и HTTPS: пошаговый гайд

Что получится в итоге:

```
ваш-домен.ru               → VPS: Caddy (HTTPS) → сайт + API в Docker + PostgreSQL (один адрес)
no-reply@ваш-домен.ru      → письма клиентам и операторам (Resend, бесплатно)
info@ваш-домен.ru          → входящие письма пересылаются в ваш личный ящик (Cloudflare Email Routing)
```

Везде ниже `ваш-домен.ru` замените на свой домен, `203.0.113.10` — на IP вашего VPS.

Порядок: **1 → 2 → 3** можно сделать уже сейчас, без сервера. Сервер — в [DEPLOY.md](DEPLOY.md).

---

## 1. Домен в Cloudflare: что проверить

1. Cloudflare → ваш домен → **Overview**: статус должен быть **Active**. Если `Pending` — у регистратора домена
   (где покупали) должны стоять NS-серверы Cloudflare, указанные на этой же странице.
2. **DNS → Records** — сюда добавляются все записи. Итоговый набор, когда всё готово:

| Тип | Имя | Значение | Прокси | Кто добавляет | Зачем |
|---|---|---|---|---|---|
| A | `@` | `203.0.113.10` | **DNS only** | вы, когда будет VPS | сайт и API ([DEPLOY.md](DEPLOY.md)) |
| A | `www` | `203.0.113.10` | DNS only | вы (необязательно) | `www.ваш-домен.ru` → редирект на основной |
| CNAME | `send` | `send.forge.rmta.net` (из Resend) | **DNS only** | Resend | Return-Path: SPF и возвраты писем |
| CNAME | `rsend` | `rsend-….forge.rmta.net` (из Resend) | **DNS only** | Resend | служебная запись Resend (Forge) |
| TXT | `resend._domainkey` | `p=MIGf…` (из Resend) | DNS only | Resend | DKIM — подпись писем |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:info@ваш-домен.ru` | — | **вы** (раздел 2.4) | DMARC |
| MX ×3 | `@` | `route1/2/3.mx.cloudflare.net` | — | Cloudflare | приём почты на `info@` (раздел 3) |
| TXT | `@` | `v=spf1 include:_spf.mx.cloudflare.net ~all` | — | Cloudflare | SPF для Email Routing |
| TXT | `cf2024-1._domainkey` | `v=DKIM1; …` | — | Cloudflare | DKIM для Email Routing |

Значения `forge.rmta.net` и ключ DKIM у каждого свои — берите из Resend, а не из этой таблицы.

**Почему везде серое облако (DNS only).** Оранжевое облако — это прокси Cloudflare. Для почтовых записей он
ломает проверку: проксированный CNAME снаружи не виден как CNAME, и Resend домен не подтвердит. Для сервера —
российские провайдеры периодически замедляли трафик через Cloudflare, а клиенты в России; HTTPS выпускает
Caddy на сервере сам (Let's Encrypt).

**Поддомен `api`.** Раньше в гайде API жил на `api.ваш-домен.ru`. Теперь сайт и API на одном адресе
`ваш-домен.ru` (`/api/v1`), поэтому отдельная запись `api` **не нужна** — ни для сайта, ни для почты.
Если вы её уже добавили — удалите или оставьте (ни на что не влияет), но адрес `https://api.ваш-домен.ru`
открываться не будет: Caddy выпускает сертификат только для `DOMAIN` из `.env`.

## 2. Отправка писем

### Вариант A — Resend + ваш домен (рекомендуется)

Бесплатно: **3000 писем в месяц, 100 в день** (на момент написания; лимиты см. resend.com/pricing).
Письма уходят от `no-reply@ваш-домен.ru` с подписью DKIM — не падают в спам.

#### 2.1. Домен в Resend
1. <https://resend.com> → регистрация → **Domains** → **Add Domain**.
2. Введите домен. Два варианта, оба рабочие:
   - **корень** `ваш-домен.ru` → отправитель `no-reply@ваш-домен.ru` (проще, так обычно и делают);
   - **поддомен** `mail.ваш-домен.ru` → отправитель `no-reply@mail.ваш-домен.ru` (репутация рассылок отдельно
     от основного домена). Тогда у всех записей ниже к имени добавится `.mail`: `send.mail`, `resend._domainkey.mail`.

   Приём почты на `info@ваш-домен.ru` (раздел 3) работает при любом варианте: Resend пишет свои записи на
   поддомены `send`/`rsend`/`resend._domainkey`, а Cloudflare — на корень `@`. Они не пересекаются.
3. Регион — любой (EU ближе к России).

#### 2.2. DNS-записи
На странице домена в Resend → **Auto configure** / **Sign in to Cloudflare** → разрешите доступ: Resend сам
создаст записи в Cloudflare. Проверьте в Cloudflare → DNS → Records, что появилось:

- **`send` — CNAME → `send.forge.rmta.net`.** Это адрес возврата (Return-Path, он же «envelope from»). Через
  него получатель проверяет **SPF** («этому серверу можно отправлять от имени домена») и сюда же приходят
  уведомления о недоставке — Resend по ним сам перестаёт слать на несуществующие ящики.
- **`rsend` — CNAME → `rsend-<регион>.forge.rmta.net`.** Вторая служебная запись новой инфраструктуры
  Resend (Forge), регион в имени (`euw1` — Ирландия) совпадает с выбранным в шаге 2.1. Ничего с ней делать не нужно.
- **`resend._domainkey` — TXT `p=MIGf…`.** Публичный ключ **DKIM**: каждое письмо подписывается, получатель
  сверяет подпись с этим ключом. Без него письма почти гарантированно уйдут в спам.

У всех трёх прокси — **DNS only** (серое облако), TTL — любой (`Auto` или `1 hr`).

> **Старая схема.** Если Resend показывает вместо CNAME другие записи — `MX send` → `feedback-smtp.…amazonses.com`
> (приоритет 10) и `TXT send` → `v=spf1 include:amazonses.com ~all`, — это прежний вариант без Forge, он тоже
> рабочий. Добавляйте ровно то, что показывает ваш экран Resend.

**Вручную** (если автонастройка не сработала): Cloudflare → DNS → **Add record**, по строке из таблицы Resend.
В поле **Name** пишите только часть до домена: `send`, а не `send.ваш-домен.ru` — Cloudflare допишет домен сам.
Ключ DKIM копируйте целиком кнопкой копирования в Resend: обрезанный ключ — частая причина «Failed».

#### 2.3. Подтверждение
1. Resend → домен → **Verify DNS Records**. Обычно 5–15 минут, в худшем случае до 72 часов.
2. Статус каждой записи должен стать **Verified**, а домена — **Verified** (зелёный).
3. Не проходит? Проверьте, что запись видна снаружи (замените домен на свой):

   ```bash
   dig +short CNAME send.ваш-домен.ru
   ```

   ```bash
   dig +short TXT resend._domainkey.ваш-домен.ru
   ```

   Первая должна вернуть `send.forge.rmta.net.`, вторая — `"p=MIGf…"`. Пусто — запись не сохранена, имя
   записано с лишним доменом (`send.ваш-домен.ru.ваш-домен.ru`) или включено оранжевое облако.
   `dig` ставится так: `sudo apt install -y dnsutils`.

#### 2.4. DMARC — добавить вручную (Resend его не создаёт)
DMARC говорит почтовикам: «письма с этого домена должны проходить SPF/DKIM; что не прошло — вот что делать,
отчёты шлите сюда». Gmail и Яндекс без DMARC режут письма чаще, а для массовых отправителей Gmail его требует.

Cloudflare → DNS → **Add record**:
- Type: `TXT`
- Name: `_dmarc`
- Content: `v=DMARC1; p=none; rua=mailto:info@ваш-домен.ru`

`p=none` — только наблюдать, ничего не блокировать: безопасно для старта. Через месяц, когда в отчётах
всё чисто, можно поставить `p=quarantine`. Адрес в `rua` должен существовать (настроим в разделе 3) — туда
почтовики будут присылать XML-отчёты. Не хотите отчётов — уберите `; rua=…`.

Проверка:

```bash
dig +short TXT _dmarc.ваш-домен.ru
```

#### 2.5. API-ключ
Resend → **API Keys** → **Create API Key**: имя `gruzspec-smtp`, права **Sending access**, домен — ваш.
Ключ (`re_…`) показывается **один раз** — сразу вставьте в `.env`. Если потеряли — удалите и создайте новый.

#### 2.6. `.env`
Локально и на сервере одинаково:

```dotenv
SMTP_HOST=smtp.resend.com
SMTP_PORT=465
SMTP_SSL=true
SMTP_STARTTLS=false
SMTP_USER=resend
SMTP_PASSWORD=re_ваш_API_ключ
SMTP_FROM=ГРУЗСПЕЦСЕРВИС <no-reply@ваш-домен.ru>
OPERATOR_EMAIL=куда-слать-заявки@example.com
```

- `SMTP_USER` — буквально слово `resend`, пароль — API-ключ.
- Домен в `SMTP_FROM` должен **точно совпадать** с подтверждённым в Resend (корень или `mail.`-поддомен).
  Ящик `no-reply@` создавать не нужно — Resend отправляет от любого адреса на подтверждённом домене.
- Закрыт порт 465 → `SMTP_PORT=587`, `SMTP_SSL=false`, `SMTP_STARTTLS=true` (или 2465 с SSL, 2587 со STARTTLS).

После правки `.env` перезапустите API (`make dev` / `make preview` заново, на сервере — `make prod-up`).

#### 2.7. Проверка отправки

```bash
make test-email TO=ваш-личный@ящик.ru
```

Скрипт покажет, через какой сервер отправляет, и либо «Готово», либо понятную ошибку. Затем:
1. Письмо должно быть во «Входящих». В Gmail откройте его → ⋮ → **Показать оригинал**: должно быть
   `SPF: PASS`, `DKIM: PASS`, `DMARC: PASS`.
2. Для оценки «попадёт ли в спам» — отправьте на адрес с <https://www.mail-tester.com>: 9/10 и выше — отлично.
3. Resend → **Emails** — там видно каждое письмо и его статус (`Delivered`, `Bounced`).

### Вариант B — Gmail (5 минут, если домена ещё нет)

Письма будут от вашего `@gmail.com`. Для демо нормально, для продакшена — вариант A.

1. В Google-аккаунте включите **двухэтапную аутентификацию** (Security → 2-Step Verification).
2. Откройте <https://myaccount.google.com/apppasswords>, создайте пароль приложения (например, «gruzspec»).
   Google покажет 16 символов — это и есть пароль для SMTP (пробелы можно убрать).
3. `.env`:

   ```dotenv
   SMTP_HOST=smtp.gmail.com
   SMTP_PORT=587
   SMTP_SSL=false
   SMTP_STARTTLS=true
   SMTP_USER=ваш@gmail.com
   SMTP_PASSWORD=пароль_приложения
   SMTP_FROM=ГРУЗСПЕЦСЕРВИС <ваш@gmail.com>
   OPERATOR_EMAIL=куда-слать-заявки@example.com
   ```

4. `make test-email TO=…`.

`SMTP_FROM` должен совпадать с ящиком, через который отправляете. Чужой адрес в «От кого» = спам.

### Что будет приходить

- **Оператору** (`OPERATOR_EMAIL`) — каждая новая заявка с телефоном, точкой в 2ГИС, фото и расчётом.
- **Клиенту** (если указал e-mail в форме) — подтверждение со ссылкой на заказ и каждая смена статуса.
- Всё отправляется из очереди с повторами: если SMTP упал, заявка всё равно принята, письмо уйдёт позже.
  Ошибки видны в админке → «Очередь уведомлений».

## 3. Приём почты на `info@ваш-домен.ru` (Cloudflare Email Routing, бесплатно)

Нужно, чтобы клиенты могли ответить на письмо, и чтобы на сайте был красивый адрес вместо gmail.

1. Cloudflare → ваш домен → **Email** → **Email Routing** (в новом интерфейсе: **Compute → Email Service →
   Email Routing**) → **Onboard Domain** / **Get started**. Проверьте предложенные DNS-записи → **Done**.
   Cloudflare сам добавит MX-, SPF- и DKIM-записи на корень домена.
   Если у домена уже есть почта (другие MX-записи) — сначала посмотрите, что там, иначе она перестанет работать.
2. **Destination Addresses** → добавьте свой личный ящик → откройте письмо от Cloudflare → **Verify email address**.
3. **Routing Rules** → **Create routing rule**: адрес `info` (и, например, `zayavki`) → действие
   «Send to an email» → ваш ящик → **Save**.
4. Проверка: напишите на `info@ваш-домен.ru` с другого ящика — письмо должно прийти (возможно, в «Спам»
   первый раз — отметьте «Не спам»).
5. В админке сайта → «Настройки сайта» → `contacts` → замените e-mail на `info@ваш-домен.ru`.

Отправка (Resend: записи `send`, `rsend`, `resend._domainkey`) и приём (Cloudflare: MX на корне `@`) друг
другу не мешают. **Не включайте** в Resend приём писем (Receiving) на том же домене — он попросит заменить MX
на корне, и пересылка на `info@` перестанет работать.

## Если что-то не работает

| Симптом | Причина и решение |
|---|---|
| `make test-email`: `smtp error: SMTPAuthenticationError` | неверный пароль: для Resend — API-ключ, логин `resend`; для Gmail — пароль приложения, не обычный |
| `smtp error: … timeout` | хостинг закрыл порт — попробуйте 587/STARTTLS или 2587/2465 (Resend) |
| письма в «Спаме» | нет DKIM/DMARC или `SMTP_FROM` не на подтверждённом домене |
| Resend не подтверждает домен | лишняя часть домена в поле Name (`send.ваш-домен.ru` вместо `send`), запись в оранжевом облаке, обрезан ключ DKIM; проверьте `dig` из раздела 2.3 |
| `make test-email`: `domain is not verified` / `403` | домен в `SMTP_FROM` не совпадает с подтверждённым в Resend (например, `@mail.` против корня) |
| `DMARC: FAIL` в «Показать оригинал» | `SMTP_FROM` на другом домене, чем подтверждён в Resend, или DKIM ещё не Verified |
| Caddy не получил сертификат | DNS ещё не обновился (`dig`), закрыт порт 80/443 в ufw или у хостера, включено оранжевое облако |
| `502 Bad Gateway` от Caddy | контейнер API не запущен: `make prod-logs` |
| в логах у всех клиентов один IP, лимиты срабатывают на всех | не задан `FORWARDED_ALLOW_IPS=*` |
